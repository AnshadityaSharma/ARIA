# Phase 5 screenshot and audio hardening — controlled evidence

`context.md` is authoritative. ARIA-owned screen recording remains excluded. This increment reuses the existing `TAKE_SCREENSHOT`, `SET_VOLUME`, `CHANGE_VOLUME`, `MUTE`, and `UNMUTE` actions, risks, parser forms, confirmation policy, and Engine boundary. No dependency was added.

## Screenshot contract

Engine resolves a `.png` destination and checks that its parent is an existing non-reparse directory and the destination is absent. The parent identity and absent destination are bound before a default LOW-risk execution or a requested LOW-risk confirmation. Confirmation cancellation, expiry, and target recheck retain the Phase 1 behavior.

The adapter creates a random private staging file in the destination directory, captures the virtual desktop with Pillow, reopens and fully decodes the PNG, verifies dimensions against physical-pixel virtual-desktop metrics when Windows supplies them, then rechecks parent and stage identity. On Windows, publication uses same-directory `os.rename`, which fails if the final name has appeared; the destination is never opened for writing. Successful Engine results include the published absolute path and decoded width/height with `VERIFIED` status. Capture, decode, geometry, recheck, or publication failure surfaces an error and removes only the staging file ARIA still owns. If another actor replaces the staging pathname, ARIA leaves that replacement untouched.

Windows display scaling can virtualize `GetSystemMetrics`. The adapter temporarily requests per-monitor DPI awareness for the metrics call and restores the prior thread context. The development machine reported 1536×960 without this adjustment and captured 3840×2400 pixels; after adjustment both reported 3840×2400. If a compatible DPI context is unavailable, OS geometry is treated as unavailable and PNG decode/dimensions still provide file-level verification. Multi-monitor and Windows 10 physical checks remain outstanding.

## Audio contract

Each operation selects one current default render/multimedia endpoint and keeps that endpoint object for its read, write, and readback. It reads both master scalar volume and mute after the write, then confirms the default endpoint ID is unchanged. `CHANGE_VOLUME` reads the current level once and clamps the requested result to 0–100. A result is `VERIFIED` only if the observed integer volume or mute state equals the requested state; its message and data reflect observed level, mute state, and endpoint ID. An unavailable or replaced endpoint, failed write, failed readback, or mismatch raises an error. The write is never retried automatically, because it may have completed before readback failed.

The adapter cannot prove that a device will remain selected after the final ID check, or that hardware will preserve a setting later. Windows may reject a write or quantize volume unexpectedly; those cases report failure instead of requested-state success. An opt-in native check wrote the currently observed level and current mute state through Engine, then restored the exact original scalar and mute values. It did not toggle mute or deliberately change loudness.

## Executed validation

- The 20 original mocked Phase 5 tests passed within the earlier full suite. They cover invalid/missing destinations, collisions, parent/stage and display-geometry changes, capture/PNG/dimension/publication failures, cleanup without deleting a replaced stage, confirmation cancellation/expiry, volume bounds, mute, device change/loss, write/readback failures, and no blind retry. This acceptance review added four deterministic fault-injection cases for permission denial and disk-full errors during capture and publication; all leave no partial output. A focused regression confirms that native-test cleanup attempts both speaker restorations and fails when the original state cannot be confirmed. The focused Phase 5 run after those additions was 25 passed, 1 opt-in native test skipped.
- Earlier full repository suite: 281 passed, 18 skipped. It was not rerun after the five focused test additions. Skips include opt-in browser/desktop/filesystem/window integrations, the opt-in native audio check, and unavailable symlink/hard-link privileges. Tests ran with a workspace temporary directory because the sandbox's default temporary directory denied writes. The opt-in native audio check passed separately (1 test) before the cleanup-hardening change; that hardware test was not repeated during this review.
- The existing Phase 1 inert kernel benchmark still runs after the audio-result contract change (20 iterations; p50/p95 full kernel 0.0534/0.0595 ms, one process and 0.0% of one logical core during a one-second idle sample). This is a compatibility smoke, not a Phase 5 real-device latency claim.
- Native Windows 11 build 26200 screenshot: repeated sets of 10 disposable 3840×2400 captures and verified publications; every PNG was removed after measurement. Native default speaker selection/readback and three same-state Engine writes passed; exact original scalar/mute were restored afterward.
- Controlled benchmark (`logs/phase5-media-controlled.json`): 30 samples per action, mocked 64×40 image and inert audio endpoint. Screenshot p50/p95 14.51/22.37 ms; set volume 0.0183/0.0300 ms; change volume 0.0184/0.0372 ms; mute 0.0170/0.0300 ms; unmute 0.0166/0.0181 ms. These exclude real capture/audio driver cost.
- Native screenshot benchmark (`logs/phase5-media-native-screenshot.json`): 10 samples, p50/p95 1144.96/1274.73 ms; process RSS after run 70.72 MiB, CPU time 10.83 s over 11.64 s wall, one process after run. A separate 10-sample repeat gave 1081.72/1287.52 ms. An earlier run on this machine gave 431.49/464.82 ms, showing scene/load-sensitive PNG timing; do not treat any run as a stable service target. Audio timings in these runs still use an inert adapter. Hardware: Intel Family 6 Model 165, 16 logical CPUs, Python 3.12.10. These are run-specific observations, not release guarantees.

## Acceptance decision — 2026-10-10

**Accepted with documented limitations.** Code review found one test-safety defect: the opt-in native audio test skipped restoration of the original endpoint if the default endpoint changed. Its cleanup now targets the originally bound endpoint, attempts both scalar and mute restoration even if one attempt fails, verifies both observed values, and fails if restoration cannot be confirmed. A deterministic regression passed. No production defect requiring a change was found. The guarded screenshot and audio contracts satisfy the scoped Phase 5 gate on the evidence above; no new dependency or resident process was added.

| Permission denial and disk-full during capture/publication | Covered by deterministic tests; native storage faults safe to defer | Injected errors confirm no final file, no owned staging file, and no success. They are not real disk-full or ACL evidence. |
