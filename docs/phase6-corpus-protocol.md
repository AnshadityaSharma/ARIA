# Phase 6 consented speech corpus protocol — version 1

This protocol prepares development and held-out evidence for the **unchanged** voice pipeline. It does not authorize recording anyone or running spoken commands against the computer. Collection starts only after each participant gives informed consent. No human recording, manifest, consent record, or transcript belongs in Git or a synchronized folder. The current repository contains no consented human corpus; the datasets and all human metrics below are **pending**.

## Enrollment, consent, and privacy

Before a session, explain the prompts, local-only processing, who can access the audio and transcripts, the retention/deletion date, and withdrawal procedure. Obtain a local consent record outside the repository. Use a pseudonymous speaker ID unrelated to a name or account; store the ID-to-person mapping only with the consent records. Use opaque, nonsensitive case IDs, family IDs, condition labels, microphone labels, and tags because IDs and labels appear in private reports or terminal output. Do not speak real private paths, accounts, contact names, passwords, or sensitive content. Use disposable example paths and application names discovered on the test machine. Store audio, reference transcripts, trial plans, manifests, and human reports in a restricted local directory outside Git/cloud sync. The test operator checks consent before invoking the opt-in live runner. The runner never saves audio or transcript text; retention for offline replay requires a separate, explicitly consented, local recording procedure. Before staging or sharing anything, inspect Git status and the exact report payload; `.gitignore` is not a privacy guarantee for files copied into the repository. Delete private material on withdrawal or the agreed retention date and invalidate reports whose source clips were removed.

## Sampling and split freeze

The collection target is **18 speakers**: six for each declared cohort (English, Indian English, Hinglish), with four development and two held-out speakers per cohort. This yields 12 development and six held-out speakers. Plan **20 intended prompts plus 10 negative manually triggered windows per speaker**: 360 intended and 180 negative trials in the target set. These are planned counts, not collected counts or a claim of statistical precision. Freeze speaker assignment before any model or parser change. No speaker or phrasing family may cross splits; no normalized reference utterance may cross splits. Keep matched category coverage in both splits while using distinct wording families. Annotators should not inspect held-out ASR outcomes while revising development prompts or code.

For each 20-prompt speaker block, target four application/disambiguation prompts, three disposable filename/path prompts, two key-combination requests (currently unsupported and expected to abstain), three numeric/percentage/geometry prompts, four other supported simple commands, two compound attempts (currently expected to abstain), and two ambiguous/unsupported requests. Include spoken names not present in tests, similar installed app names, literal filenames with dots/underscores, position and percentage phrasing, and Hinglish code-switching. A category can overlap linguistically, but its primary category is fixed in the trial plan. Ten negative windows contain silence, incidental room speech, or noise after a deliberate manual trigger; they are not ambient always-on listening trials.

Balance quiet and ordinary-background-noise sessions; built-in and headset microphones where available; near/normal/far distance; natural slow/normal/fast rate; short and long pauses. Record OS build, CPU, audio device type, input format, distance band, room/noise label, date/session ID, and whether an overflow or device switch occurred. Keep conditions realistic and record deviations. Do not resample or denoise retained clips before the primary baseline. Capture is the production 16 kHz mono float32/50 ms path during live trials; consented retained WAVs should be lossless, locally stored, hashed, and linked to the same trial ID. The offline decoder may resample a WAV, so its results must be labeled **file replay**, separate from the live capture result.

## Annotation and exclusions

Before inference, record the exact audible reference words, including code-switched wording; ignore punctuation/case for WER, but do not silently rewrite words to match the ASR. Fix a romanization convention for repeated Hinglish terms before scoring. Record the intended result as a validated typed action with its **raw parser target** and exact parameters, or `clarify`/`abstain`. Unsupported key chords, compound requests, and genuinely ambiguous requests must not be relabeled as successful single actions. For dynamic application ambiguity, annotate both the extracted raw name and a separate adjudication note about the machine's installed-app set; the current replay/live runners measure extraction proposals, not OS target resolution. Two annotators independently review a sample and adjudicate all disagreements before a split is frozen. Keep correction history rather than replacing the old annotation without a version record.

Exclude a clip from ASR/WER only for revoked consent, corrupt/unreadable audio, wrong speaker, missing reference, or a documented collection protocol failure. Record every exclusion with case ID, reason, date, and split before examining model performance. Do not exclude noisy, accented, low-confidence, empty-transcript, or incorrect-command cases merely because they hurt a score. Keep device failures in the live-trial denominator and report them separately. Reference-empty negative clips contribute no WER denominator but remain in the negative-triggered denominator.

Freeze **v1** by hashing each consented audio file and the private development and held-out manifests, recording the parser/voice source hashes and package versions, and writing a private freeze ledger with counts per cohort, speaker, condition, microphone, action category, and expected outcome. A second evaluator checks split leakage and annotation completeness. After freeze, additions go to **v2** with new IDs and hashes; corrections create a new version with reason, old/new annotation, and adjudicator. Never silently mutate a reported held-out set. Re-evaluate the unchanged baseline on the new version before comparing any future optimization.

## Safe trial and replay sequence

1. Prepare private `human_live` development and held-out trial plans outside the repository. Each JSON file has `version: 1`, `source: "human_live"`, its `split`, and `cases`. A case uses the same annotation fields as the offline manifest except audio path/hash, plus `kind: "intended"` or `"negative"`; it includes an absolute outside-repository `consent_record`. Intended trials need nonempty reference words; empty references are reserved for appropriate negative trials. The operator presents prompts privately; the runner prints only case IDs and trial kind. Its validation rejects missing consent, duplicate IDs, and speaker/family/reference leakage across splits.
2. Validate **both** plans in one invocation without opening the microphone: `.venv\Scripts\python.exe scripts\phase6_live_voice_trials.py --plan C:\private\aria-voice\development-live.json --plan C:\private\aria-voice\held-out-live.json`. This is the default mode. Cross-split leakage checks operate across files supplied together; separate one-file validations cannot establish split isolation. A reviewer must also inspect near-duplicate phrasing that the exact normalized-text check cannot detect.
3. After consent is reconfirmed, run the same two-plan command with `--consented-live --output C:\private\aria-voice\live-report.json`. The operator presses Enter for each trial. The runner uses `Microphone` and `VoiceController.prepare()` with the unchanged ASR/confidence/parser path and an interpret-only engine whose execute/confirm methods fail. It discards the in-memory audio buffer and transcript after scoring each trial. It does **not** send a hotkey or execute a command. The report is private, created without overwrite, and contains no audio or transcript text; metrics are separated by split and cohort. An interrupted session is marked as incomplete.
4. If the participant separately consented to retained audio, collect lossless WAVs with an approved local procedure, keep them outside the repository, and create `human` development/held-out manifests as defined in [phase6-voice-baseline.md](phase6-voice-baseline.md). Run `scripts/phase6_voice_baseline.py` locally. Never infer live capture behavior from this replay.
5. Adjudicate mismatches locally by comparing capture/endpoint evidence, observed final ASR text from a separately consented retained clip or private rerun, reference-text interpretation, ASR-text interpretation, target resolution, policy, and execution evidence. The live report contains case IDs, condition labels, timings, resource samples, and outcome scores, but omits audio and transcript text; a non-retained trial cannot later be replayed for detailed ASR error attribution. A separate controlled, disposable Engine study is needed for speech-to-**verified-result** latency; the live runner deliberately cannot produce that metric.

## Metric denominators and evidence labels

WER is total Unicode word edit distance divided by total reference words on intended clips with reference words; include rejected/empty ASR outputs as deletions. Empty-reference trials contribute neither WER errors nor reference words; unexpected words on those trials are assessed through proposal outcomes instead. Exact complete proposal requires the correct outcome and, for an action, capability, raw target, and parameters. Capability accuracy uses expected-action trials; target and argument accuracy condition on correct capability. **Negative-triggered command proposal rate** is action proposals divided by all negative manually triggered trials. It is a live microphone negative-window measure, **not** an ambient or real hotkey false-trigger rate. **Missed complete-command rate** is expected-action intended trials without a completely correct action proposal divided by all expected-action intended trials, including capture/ASR failures. Report silence, overflow, device failure, confidence rejection, ASR mismatch, and interpretation rejection separately. An action proposal is not an executed false action.

The live runner records microphone request-to-ready, capture/endpoint interval, an estimated first above-threshold 50 ms block when audio is available, speech-end-to-final transcript, ASR, and interpretation timings. The first-above-threshold marker is a post-hoc estimate from the returned buffer, not a separate device timestamp. It records process CPU time and after-trial RSS samples, not peak or long-idle usage. The model load is one cold-process sample; subsequent trials share the loaded model. Report p50 only with at least 10 comparable samples and p95 with at least 20, stratified by cohort, microphone, noise, and length where denominators allow. The current pipeline emits no partial transcript, so first-partial latency is unavailable. Speech-to-verified-result needs separate safe Engine execution evidence. Do not combine synthetic replay, human file replay, manually triggered live capture, and real hotkey/UI runs into one accuracy or latency number.
